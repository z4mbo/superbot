# Superbot hosting

Superbot supports multi-account authentication, shared Spaces and live updates. Each person signs in separately. A new account's **Personal** Space starts with the account holder as its only member. The owner can invite people into it or create a separate Space for team work. Each invite grants access to its selected Space, and link invites work with mail disabled. The base stack needs no model credentials for signup, sharing or membership. Bot inference requires a model connection. This stack starts with computer sandboxes disabled.

## Start on your machine

Install Node 24.15 or later in the 24.x line, or Node 26 or later, and Docker with Linux containers and Compose 2.24.4 or later. Run from the checkout root.

```sh
node infra/superbot/host.mjs init
node infra/superbot/host.mjs up
node infra/superbot/host.mjs status
```

Open `http://127.0.0.1:5173`. The first run builds the API, worker and web app from this checkout, initializes Postgres 18 and applies migrations before starting the API. The API, worker, database and web containers should be healthy. Migration and data initialization should exit with code 0. For startup output use `node infra/superbot/host.mjs logs`.

The initializer writes `.env.superbot.local` once with separate random credentials. Keep it private and back it up with the project-scoped database and application data volumes. `node infra/superbot/host.mjs down` stops the stack and keeps its volumes. Use `init --port 55783` for a different loopback port. For a second stack, pass a unique `--project NAME` and a separate `--env FILE` to every command, and choose an unused port at initialization.

Sign up in two separate browser profiles to try multiplayer on one machine. In the Space's settings, choose **Invite** and then **Copy invite link** and open the link in the other profile. Each link can bring in one account and expires after seven days. For teammates on other machines, use a shared HTTPS origin.

## Host on another machine

For a persistent NixOS host with private access from Macs and Windows PCs, see [NixOS hosting](nixos-hosting.md).

Run the same checkout and bootstrap on the server with the public-facing HTTPS origin.

```sh
node infra/superbot/host.mjs init --origin https://superbot.example.com
node infra/superbot/host.mjs up
node infra/superbot/host.mjs status
```

Point DNS at the HTTPS reverse proxy. Run the proxy on the Docker host and forward the entire origin to `http://127.0.0.1:5173`. Preserve the original Host header and forward client and protocol information from the trusted proxy. Allow streaming responses without buffering and preserve WebSocket upgrades for clients that use them. The bundled web server forwards auth and RPC traffic to the internal API. See [proxy and client-address configuration](../self-host-production.md#client-addresses).

For the example domain, add this to the host's Caddyfile.

```caddyfile
superbot.example.com {
  reverse_proxy 127.0.0.1:5173
}
```

The remote HTTPS configuration closes signup by default. With mail, set `SIGNUPS_ENABLED=true` and an explicit `SIGNUP_ALLOWLIST` before starting. An allowlist requires recipients to verify their mailbox. To keep registration closed, privately provision each intended account using the existing account bootstrap. Export `OWNER_EMAIL` and `OWNER_PASSWORD` in the current shell, run `node infra/superbot/host.mjs account` for that account, then remove both variables from your shell. The password must have at least 16 characters. The command creates an ordinary verified account with a personal Space. A Space owner still grants access to a shared Space separately. For an installation without mail, limit access to a trusted network. See [account policies](../self-host-accounts.md).

For an existing stack, edit `WEB_ORIGIN` and `BETTER_AUTH_URL` together to move to a new origin, then rerun `up`. Keep database credentials and the encryption key. People may need to sign in again and owners should reissue links carrying the old origin.

## Enable isolated agent computers

Use a Linux Docker Engine with the iptables firewall backend and volume subpath support (Docker Engine 26 or later). Review the [upstream restricted egress rules](../self-host-docker-computers.md#restricted-computer-egress) before enabling the feature. The rules change the Docker host's firewall for all matching computer bridges. The launcher never installs them. On NixOS follow the [NixOS procedure](nixos-hosting.md#enable-isolated-agent-computers).

On an existing stack, stop it with the launcher before changing the environment file. Keep its project name, database credentials and encryption key. Ensure the environment file contains a distinct `SANDBOX_SUPERVISOR_TOKEN` (generated by `init`; use `openssl rand -hex 32` privately if missing) and set:

```dotenv
SUPERBOT_COMPUTERS_ENABLED=true
```

Run `node infra/superbot/host.mjs up` and then `node infra/superbot/host.mjs egress` with the same environment and project options. Expect verified restricted egress. The supervisor refuses to provision a computer if the rules cannot be verified. On hosts with private DNS resolvers, see the upstream guidance for `SANDBOX_COMPUTER_DNS`.

New agents default to a dedicated Linux computer. An existing agent keeps its saved mode. In its settings, select the dedicated mode for an existing agent that should have its own computer, then open **Computer** and start it. The toggle for shared Team Computers remains available. Screen access uses the existing signed, scoped web proxy at the app origin. Only the supervisor receives the Docker socket. The web port stays on loopback, and sandbox computers receive neither host folders nor GPUs.

To disable computers, stop the agents' computers in the app, run `host.mjs down` with the enabled environment, remove `SUPERBOT_COMPUTERS_ENABLED` from that file, then run `host.mjs up` with the same project and environment. The agent choices and persisted homes remain in the project volumes.

## Connect external apps

A fresh host offers direct connections to Atlassian, GitHub, Linear and Notion.
Each person authorizes their own account. The GitHub preset takes a personal access
token. Linear, Notion and Atlassian use their hosted sign-in pages. Provider plan,
workspace policy and granted scopes determine which tools the account may use.
[GitHub remote server](https://github.com/github/github-mcp-server) ·
[Linear MCP](https://linear.app/docs/mcp) ·
[Notion MCP](https://developers.notion.com/guides/mcp/get-started-with-mcp) ·
[Atlassian OAuth](https://developer.atlassian.com/cloud/rovo-mcp/guides/configuring-oauth-2-1/)

The Slack, Gmail, Google Calendar and Google Drive presets use registered OAuth
clients. Register a client with the provider and enter its client ID and, when
required, its secret in the connection settings. Google's Workspace MCP endpoints
require access to its Developer Preview, the corresponding product and MCP APIs
enabled, and an OAuth client marked for use by an AI-powered agent.
[Slack MCP](https://docs.slack.dev/ai/slack-mcp-server/) ·
[Google Workspace MCP setup](https://developers.google.com/workspace/guides/configure-mcp-servers)

For the wider managed app catalog, configure the integration provider in the
deployment's private environment file and restart the stack. The API and the worker
need the same provider configuration. [Integration provider settings](../self-host-integrations.md)

## Enable community plugin review

Choose a verified account on the deployment to moderate submissions. In the environment file created by `init`, set `SUPERBOT_ADMIN_EMAILS` to its email address. Separate multiple reviewers with commas. Run `node infra/superbot/host.mjs up` to apply the setting. In **Plugins**, the reviewer can open **Review** to inspect and approve a publisher's version. An approved version appears in **Discover** on this server. The [plugin toolkit](plugin-toolkit.md) also supports review from the terminal.

## Optional private access with Tailscale

Use the host's MagicDNS HTTPS origin at initialization, for example `--origin https://superbot.example-tailnet.ts.net`. Start the loopback stack, then run these commands on the connected host.

```sh
tailscale serve --bg http://127.0.0.1:5173
tailscale serve status
```

Use the origin shown by Serve for all clients and invite links. Tailscale requires a signed-in host, HTTPS support on its tailnet and access for each teammate's device. The app still requires a Superbot account. To turn off the default Serve endpoint use `tailscale serve --https=443 off`. See [Tailscale Serve](https://tailscale.com/docs/reference/tailscale-cli/serve).

## Optional email invites

Configure transactional SMTP in the stack's environment file and rerun `up`.

```dotenv
EMAIL_PROVIDER=smtp
SMTP_URL=smtps://smtp-user:percent-encoded-password@smtp.example.com:465
EMAIL_FROM=superbot@example.com
```

Use a sender authorized by your SMTP server. For a STARTTLS server, use `smtp://` with its SMTP submission port. The existing account-mail adapter requires TLS and validates the server certificate. The SMTP server must be reachable from the API container.

In Space settings, choose **Invite** and then **Invite by email**. The recipient opens the link and signs in or registers under the server's account policy. A Space invitation grants membership once used. Treat the single-use link as a secret because it can be forwarded. To bind an invitation to a specific verified mailbox and grant organization membership, use the separate organization invitation. With email disabled or unavailable, use the copy-link flow and share the link privately.

## Isolated verification

Use a fresh Postgres 18 cluster, a dedicated application data directory and a local Mailpit instance with SMTP relaying disabled. Give the web, API, Postgres and Mailpit listeners unused loopback ports. Create a disposable environment file outside the checkout, using `init --env FILE --port 55783` for fresh secrets. The following native fixture procedure uses the repository dependencies and local Postgres, Mailpit and OpenSSL executables.

1. Start Postgres on `127.0.0.1:55483` in a new temporary directory. Set `DATABASE_MIGRATION_URL` to its owner connection and `DATABASE_URL` to the separate `rakazo_app` login with a fixture password. Set `RAKAZO_DB_PACKAGE_DIR` to the absolute path of `packages/db` and `RAKAZO_ENV_FILE=none`. Run `pnpm db:generate` then `pnpm db:migrate`. Migration creates the runtime login.
2. Generate a temporary SMTP certificate and private key with `openssl req -x509 -newkey rsa:2048 -nodes -days 2 -subj /CN=localhost -addext subjectAltName=IP:127.0.0.1 -keyout smtp-key.pem -out smtp-cert.pem`. Run `mailpit --listen 127.0.0.1:58025 --smtp 127.0.0.1:51025 --smtp-tls-cert smtp-cert.pem --smtp-tls-key smtp-key.pem --smtp-require-starttls` from the temporary directory.
3. In the API's shell, keep the runtime `DATABASE_URL` and clear `DATABASE_MIGRATION_URL`. Set `DATA_DIR` to a fresh temporary directory, `RAKAZO_ENV_FILE=none`, `NODE_ENV=production`, `API_HOST=127.0.0.1`, `API_PORT=53100`, `SANDBOX_PROVIDER=none`, `WAKEUP_DRIVER=graphile`, `EMAIL_PROVIDER=smtp`, `SMTP_URL=smtp://127.0.0.1:51025`, `EMAIL_FROM=fixture@example.test` and `NODE_EXTRA_CA_CERTS` to the absolute path of the fixture certificate. Run `node --env-file FILE --import tsx apps/api/src/index.ts` with the generated fixture file. The shell's SMTP setting takes precedence over the file's default.
4. In a separate shell, set `API_PROXY_TARGET=http://127.0.0.1:53100`, `RAKAZO_ENV_FILE=none` and `RAKAZO_ALLOW_DEV_SECRETS=1`. Run `pnpm --filter @rakazo/web exec vite --host 127.0.0.1 --port 55783 --strictPort`. With a fresh mailbox, run the smoke script below. Stop only the fixture processes and database when finished.

```sh
node infra/superbot/check-multiplayer.mjs http://127.0.0.1:55783 http://127.0.0.1:58025 --disposable
```

The smoke creates synthetic accounts and Spaces and checks the owner's email verification, captured invitation, invite redemption, role boundaries and the roster notification delivered when the guest joins. It requires a disposable stack because it writes data. The Compose definitions can also be inspected with `docker compose --env-file FILE -f infra/compose/docker-compose.yml -f infra/superbot/compose.yml config --services`.

### Verification status

The native fixture passed with PostgreSQL 18, the built API and web preview, and local Mailpit over STARTTLS. The worker build passed and the native worker connected to the fixture job queue. The account bootstrap created a verified fixture account that could sign in. The existing Space membership and SMTP suites passed all 46 tests. Local and remote definitions resolved with Compose 2.40.3. The full container build and startup still require a Docker Engine. Public HTTPS and Tailscale were not exercised.
