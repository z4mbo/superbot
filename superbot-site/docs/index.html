Plugins

Build a plugin

A Superbot plugin is one JSON manifest that adds skills, tools or record apps to the bots people choose. This guide takes you from an empty folder to an approved version with the superbot-plugin command.

In the desktop app, open Plugins and choose Create plugin to define a skill or connector and submit a version. Under Yours you can follow its review status. The CLI and registry API use the same manifest format.

What a plugin can add

  • Skills: Markdown instructions that teach a bot when and how to do something. Up to 16,000 characters each. Bots read them as untrusted input.
  • Tools: a remote MCP server reached over Streamable HTTP at a public HTTPS address. A person approves every call after seeing its destination and arguments.
  • Record apps: a list of entries with fields you declare, such as a date, a meal and its calories. Superbot stores the entries and shows them in its own form and list. You write no code and run no server.

A plugin has 1 to 16 parts, in any mix. It cannot carry credentials, HTTP headers, commands, packages, hooks or any field the schema doesn't name. The server stores the manifest and never runs code from it.

Record apps in plain terms

A record app is a small database with a fixed set of fields. The person who installs it adds and removes entries in Superbot. A bot they grant it to can read the same entries and propose new ones. Superbot draws the same form, list and total for every record app. A plugin can't bring its own screens, HTML or JavaScript.

The mcp-app starter of superbot-plugin init is a tool server, not a record app. It writes an MCP server that you host yourself.

From folder to approved version

  1. Create a starter skill. This writes plugin.json with one skill part whose id is summary. The slug, release-notes here, is your plugin's permanent global name: 1 to 64 lowercase letters and digits with single hyphens between words. Choose another if it's taken.
  2. Edit the manifest. A plugin with a skill and a tool looks like this: For a working tool example, run superbot-plugin init temperature-tool --template mcp-app in an empty directory, then start node server.ts. Its README includes a local tool call and public HTTPS deployment steps. Set your manifest endpoint to your deployed address. Every field is in the manifest reference.
  3. Validate it. superbot-plugin validate checks the schema locally without contacting the server. The registry checks the endpoint's safety during review.
  4. Publish version 1. The version comes back as JSON with status pending. Your first submission reserves the slug for your account.
  5. Wait for review. A deployment admin approves or rejects it. superbot-plugin status VERSION_ID shows the status and any rejection reason.
  6. Install and grant. Once approved, anyone signed in to the server can install it into their Space. Installing adds nothing to any bot until someone grants parts to a bot. See review, install and grants.

Walk through the Calorie diary

The Calorie diary is an approved record app with the slug kcal-diary. A new server publishes it in the store unless another publisher already holds that slug. Its whole manifest is three fields and a total. The repository keeps it in examples/plugins/kcal-diary/plugin.json, and superbot-plugin init kcal-diary --template kcal-diary writes the same file.

  1. Install it. Find Calorie diary in the store's Discover list and choose Install. Nothing is installed for you in advance. The diary belongs to your account in the selected Space, and other members of the Space can't see your entries. They install their own diary.
  2. Log meals. Open the diary. Add an entry with a date, a meal and its calories. Use the day arrows or Today to see one day's entries and calories, or All dates for everything. The total counts every matching entry, including entries not yet loaded on the page.
  3. Fix a mistake. An entry can't be edited. Remove it and add a corrected one. Only people remove entries. A bot can't remove them.
  4. Give a bot access. Under Installed, select one of your bots and turn on the meals part. Other bots stay without access until you turn it on for them too.
  5. Ask the bot. In a direct chat with that bot, ask “What have I eaten today?”. The bot can list entries and the total without asking you first. Then ask it to add a 220 kcal snack for today. The approval card shows the values it wants to save. Nothing is saved until you choose Allow once. In a Space set to Never ask, the addition is refused.

A bot can use the diary only in a direct chat with you, in a turn your own message started. It has no access in group conversations or in turns started by someone else's message. When the bot answers with a model CLI installed on your computer, Superbot sends that CLI the prompt alone, so the bot can't read or add entries in those turns. Turning off the bot's meals part keeps your entries. Uninstalling the diary permanently deletes them. Record app data and versions covers the rest.

Publish your own record app

Anyone with an account on the server can submit a record app. Start from the diary, change the name, description and fields, then submit it under a slug of your own. kcal-diary already belongs to the bundled diary.

validate checks record app fields with the same limits as the server. A deployment admin then reviews the version like any other. Once it is approved, people find it in Discover and install it for themselves. superbot-plugin only writes, checks and submits manifests. It can't open an app or read, add or remove entries.

Writing a good skill

  • Say when to use it in the first sentence, then how.
  • Name the tool parts it relies on by their part id, so a bot without that grant knows to ask.
  • Don't ask the bot to reveal, store or send secrets.
  • Write guidance, not rules that override the person. Bots treat skills as untrusted input.

Writing a good tool server

  • Support MCP initialization, tools/list and tools/call over Streamable HTTP. Keep listing free of side effects.
  • Give each tool a short description and a JSON object input schema with its required fields, and validate arguments again on your server.
  • Keep arguments short. People read them in the approval card before every call.
  • Treat the endpoint as public and set your own rate limits. Redirects and private addresses fail at runtime.
  • Publish a new version when the manifest or a tool's contract changes incompatibly.

Plugins from GitHub repositories

The server Superbot builds on can also install plugins from a public GitHub repository using plugin.json and mcp.json in a different format. That format is documented in docs/build-a-plugin.md in the repository. These pages cover the Superbot store, which uses the manifest above and a review step.
